Смотрю на всю подборку вакансий (порядка 20 обсуждённых) и считаю, что повторялось чаще всего:

1. Тестирование (unit/integration) — самый частый пробел, встречался почти в каждом письме.
Это не отдельная технология, а практика — pytest для Python, Jest/Vitest для JS. Дешевле всего закрыть: начать реально покрывать тестами один-два текущих проекта (например, критичные части платёжного движка или SEO-пайплайна), и в резюме/откликах это перестанет быть "не системно".

2. Kubernetes — второй по частоте.
Встречался в Manufex, Kick Health, банковском PHP/Yii2, Neoflex — везде, где Docker Compose уже не хватает. Не нужно становиться DevOps-инженером — базовое понимание (читать манифесты, kubectl logs, деплой в существующий кластер) закрывает формулировку "базовое понимание K3s/K8s", которая много где just checkbox, а не hard requirement.

3. RabbitMQ или Kafka — конкретно, а не через Celery/Redis-аналог.
Функционально ты закрываешь этот класс задач, но название инструмента в резюме важно для ATS-фильтров и HR. Проще: поднять RabbitMQ в одном текущем проекте вместо/рядом с Celery — не архитектурная революция, а один вечер интеграции.

4. LangChain или LlamaIndex + любая векторная БД (Qdrant или pgvector — раз PostgreSQL уже есть).
AI-роли явно растущий сегмент среди вакансий, что тебе прилетают, и "ручная оркестрация без фреймворка" каждый раз звучит как оправдание. Формализовать один из existing пайплайнов (например, SEO Decision Engine) через LangGraph — закроет сразу и "agent orchestration frameworks", и RAG-пункты, если добавить pgvector для поиска по накопленным данным.

5. Vue.js — точечно, если приоритет на PHP/Laravel-вакансии.
Встречался 3 раза именно в связке с Laravel. Учитывая, что React уже сильная база, разница в переходе не архитектурная, а синтаксическая — можно закрыть за 1-2 недели прицельного проекта.

Низкий приоритет (редко и specialized, не стоит распылять время):

Golang — всего 2 вакансии, и там это часто единственный blocking-фактор из многих требований, не факт, что окупится.
ML/CV-стек (PyTorch, CAD-парсинг) — это отдельная профессия, не "докрутка стека".
Ruby on Rails, банковский compliance (PCI DSS/152-ФЗ), офлайн-LLM/llama.cpp — слишком нишевые и объёмные, чтобы добавлять ради конкретных вакансий.

По каждому пункту — куда встроить в существующее, где нужен отдельный demo:

1. Тесты — встраиваем в существующее, без демо-проекта.
Лучший кандидат — Multi-Chain Payment & Reconciliation Engine: там уже есть чёткая бизнес-логика с edge-кейсами (unique-amount+memo сверка, idempotent webhook, underpayment guard, round-robin роутинг) — это готовый набор unit-тестов "из коробки", писать их не выдумывая сценарии, а формализуя то, что уже разбирал руками. Плюс — Weakness Scorer/Decision Engine в domain_search (детерминированная логика скоринга — идеальный кандидат для pytest с параметризованными кейсами). Начни с payment engine — там цена ошибки нагляднее всего объясняется на собеседовании.

2. Kubernetes — можно и на существующем, и как отдельный мини-демо.
Вариант А (быстрее): взять любой уже задеплоенный на Railway проект (например, GEO-Optimizer SaaS — FastAPI+Celery+Redis+Postgres, готовая многосервисная архитектура) и написать k8s-манифесты для него — Deployment/Service/ConfigMap для каждого компонента, развернуть локально через k3s или kind. Не нужно реально мигрировать прод — достаточно, чтобы манифесты существовали и ты мог их показать/объяснить.
Вариант Б: отдельный игрушечный демо — 3 контейнера (API + worker + Redis) специально под k8s, если не хочется трогать боевой проект даже локально.

3. RabbitMQ — точечная замена в одном месте.
Не переписывать всю очередь — добавить RabbitMQ как второй брокер рядом с Celery+Redis для одного изолированного потока, например, обработку webhook'ов от SePay/блокчейн-эксплореров в payment engine (там естественная точка входа с уже понятной семантикой "событие → обработка"). Это даст конкретный пример "делал на RabbitMQ", а не абстрактный.

4. LangChain/LlamaIndex + векторная БД — формализация существующего пайплайна.
Самый естественный кандидат — Decision Engine в domain_search SEO Pipeline (сейчас ручная последовательность: keyword generation → SERP parsing → clustering → scoring → ROI → decision). Переписать этот конкретный поток на LangGraph — граф состояний с условными переходами (например, при ALARM сразу выход, минуя ROI-расчёт) — это именно то, для чего LangGraph и нужен, и звучит убедительно на интервью, потому что ты знаешь логику пайплайна досконально.
Для векторной БД — добавить pgvector (раз PostgreSQL уже везде) в domain_search для семантического поиска по накопленным кластерам ключевых слов или в SEO Content Tool для поиска похожего сгенерированного контента — избегания дублей между статьями.

5. Vue.js — нужен отдельный демо, встраивать некуда.
В текущих проектах фронтенд везде на React, смысла переписывать нет. Сделай маленький автономный demo — например, копию одной уже существующей панели (админка плагина-CRM для букмекеров или дашборд GEO-Optimizer) на Vue 3 + Composition API + Pinia. Не весь проект — один экран с таблицей, фильтрами и формой, чтобы было что показать и о чём говорить конкретно.
